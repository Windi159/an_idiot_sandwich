## 1. 평가 체계

점수 없이 바꾸면 좋아졌는지 알 수 없어서 이것부터 만들었어요.

### 1-1. RAGAS 자동 평가 (`scripts/ragas_eval.py`)

- **방식:** 서버 API를 앱처럼 호출해 답을 받고, RAGAS로 5개 지표를 채점해요.

  | 지표 | 뜻 |
  |---|---|
  | 충실도 | 답이 찾은 문서에 근거하는지. 낮으면 지어낸 말이 많다는 뜻 |
  | 답변 관련성 | 답이 질문에 맞는 답인지 |
  | 검색 정밀도 | 찾은 문서 중 쓸모 있는 문서가 위쪽에 있는지 |
  | 검색 재현율 | 정답 내용이 찾은 문서 안에 들어 있는지 |
  | 정답성 | 답과 정답이 얼마나 겹치는지 |

- **왜:** "답이 틀렸다"만으로는 원인을 알 수 없어요. 검색이 틀렸는지, 모델이 지어냈는지를 나눠 봐야 고칠 곳이 보여요.
- **심판:** 외부 API를 쓰지 않으려고, 이 PC에서 도는 기본 Gemma 4 12B 4비트가 채점해요.
- **실행:** PEP 723 스크립트라 `uv run scripts/ragas_eval.py`로 돌려요. 서버 `.venv`에는 ragas가 없어요.

### 1-2. 답변 모으기와 채점 분리

- **수정:** `--no-score`(답만 모으기)와 `--answers <파일>`(모은 답만 채점) 옵션을 추가했어요.
- **왜:** LoRA나 Qwen처럼 서버 모델을 바꿔 시험할 때, 그 모델이 자기 답을 채점하면 공정한 비교가 아니에요. 그래서 답은 시험할 모델로 모으고, 채점은 늘 같은 기본 Gemma로 해요.

### 1-3. 전체 다시 채점 (10-29~30)

- **왜:** 3·4번은 LoRA를 얹은 모델이 자기 답을 채점한 사실을 나중에 발견했어요.
- **결과:** 9개 버전을 같은 심판으로 다시 채점했더니 변화는 모두 ±0.015 안이었어요. 결론은 바뀌지 않았어요. 채점 자체의 흔들림은 ±0.01 정도로 봐요.

### 1-4. 비교 노트북 (`notebooks/ragas_report_all.ipynb`, HTML, 엑셀)

- **방법:** `tmp/make_notebook.py`와 설정 `tmp/config_all.py`로 노트북을 만들어요 (pandas, matplotlib).
- **들어 있는 것:**
  - 버전 설명표
  - 버전별 점수 그래프, 정답성과 응답 시간을 같이 본 그래프
  - 문서별 정답성 표
  - 틀린 원인 분류 (검색 실패 / 지어냄 / 답 부족 / 양호)
  - 두 버전의 문항별 비교, 엑셀 내보내기
- **수정한 것:**
  - 폴더 이름(날짜) 대신 버전 이름을 붙였어요.
  - 9개를 겹쳐 그리면 알아볼 수 없어서 상자 그림을 썼어요.
  - `SETS=["글"]`로 음성 문항을 뺐어요.
  - 서버 `.venv`를 건드리지 않으려고, 노트북은 임시 uv 환경에서 실행해요.

## 2. 개선 작업 (버전 순서)

### 2번. 검색 미세조정 A (KR-SBERT 임베딩): 채택

- **기술:**
  - 검색용 임베딩 모델 `snunlp/KR-SBERT-V40K-klueNLI-augSTS`를 우리 문서로 다시 학습했어요 (`finetune/train_embed.py`).
  - 학습 데이터는 로컬 Gemma가 문서마다 만든 질문 4개예요: 정식 질문, 반말, 짧은 키워드, 상황 설명형 (`finetune/gen_embed_data.py`).
  - 손실 함수는 MultipleNegativesRanking이에요. 질문을 정답 문서에는 가깝게, 헷갈리는 오답 문서와는 멀게 만들어요.
- **왜:**
  - 기준 버전에서 틀린 이유 1위가 **검색 실패**(98문항)였어요.
  - 원래 모델은 일반 문장용이라 "PSD 505", "부가운임" 같은 역무 용어를 잘 구분하지 못했어요.
- **신경 쓴 점:**
  - 테스트 세트와 비슷한 질문은 학습 데이터에서 뺐어요. 시험 문제가 학습에 새면 점수가 부풀려지기 때문이에요.
  - 학습 질문의 10%를 떼어 두고, 그걸로 가장 좋은 에폭을 골랐어요.
- **수정:** 미세조정 뒤 점수 분포가 달라져서 검색 문턱을 0.5에서 0.45로 낮췄어요.
- **결과:** 정답성 0.355→0.549, 검색 재현율 0.53→0.80, 검색 실패 98→36문항.

### 3·4번. 답변 미세조정 B (Gemma 4 12B QLoRA): 채택 안 함

- **기술:**
  - Gemma 12B를 4비트(NF4)로 올리고, 언어 모델 부분에만 LoRA를 달아 학습했어요 (`finetune/train_llm.py`, peft, bitsandbytes). 음성·이미지 인코더는 건드리지 않았어요.
  - 학습 데이터는 RAFT 방식으로 1,160개 만들었어요 (`finetune/gen_llm_data.py`).
    - 정답 문서만 준 Gemma가 모범 답을 써요.
    - 학습 입력에는 실제 검색 결과처럼 문서 3개를 붙여요.
    - 일부는 정답 문서를 빼고 "모르겠다"고 답하게 해서, 지어내지 않는 법을 배우게 했어요.
  - 학습 뒤 GGUF로 바꿔 llama.cpp 서버에 얹었어요.
- **왜:** 답 형식(존댓말, 짧게, 방송 문안은 그대로)과 "문서에 없으면 모른다고 하기"를 모델에 직접 가르치려고 했어요.
- **결과:**
  - **3번 (4비트 QAT + LoRA):** 정답성 0.515로 A만 쓸 때보다 낮았어요. "모르겠다" 답이 26개에서 36개로 늘었고, 단어만 나열한 답도 생겼어요.
  - **4번 (8비트 일반판 + LoRA):** 학습은 일반판으로 하고 서버는 QAT판을 써서 생긴 차이인지 확인했어요. 0.543으로 A와 비슷했고, 응답은 2배 느려졌어요.
- **결론:** 4비트·8비트 어디에 얹어도 A를 넘지 못했어요. 살리려면 학습 데이터를 고쳐야 해요.

### 5번. Qwen3-Omni 30B: 채택 안 함

- **기술:** 30B MoE 모델을 MXFP4로 직접 양자화해 16GB GPU에 올렸어요.
- **왜:** 더 큰 모델이면 답이 나아지는지 확인했어요.
- **결과:**
  - 정답성 0.540으로 Gemma와 비슷했어요.
  - 응답이 2.73초로 2.4배 느렸어요.
  - 업무 질문 10개를 잡담으로 잘못 분류해 답하지 않았어요.

### 6번. 문서 5개 + 답변 단계 음성 빼기: 채택

- **기술:**
  - `STS_RAG_TOP_K` 3→5: 모델에 넘기는 문서를 5개로 늘렸어요.
  - `STS_QA_AUDIO=false`: 새로 만든 설정이에요 (`config.qa_audio`, `pipeline._qa_messages`).
- **왜:**
  - **문서 수:** 정답 문서가 4~5위에 걸려 빠지는 경우가 많았어요.
  - **음성 빼기:** 음성 질문은 받아쓰기 단계와 답변 단계에서 음성을 두 번 처리했어요. 답변 단계에는 받아쓴 글만 넣어도 돼서 두 번째 처리를 없앴어요.
- **결과:**
  - 정답성 0.549→0.573, 충실도 0.889→0.927.
  - 음성 질문 응답 1.92초→1.67초. 14개 중 13개 답이 같아 정확도 손해는 없었어요.

### 7번. 리랭커: 채택 (지금 `.env`)

- **기술:** 크로스 인코더 `dragonkue/bge-reranker-v2-m3-ko`가 임베딩이 고른 상위 20개를 질문과 한 쌍씩 다시 읽어 순서를 다시 매겨요 (`rag.py`의 `ranked()`, `rerank_scores()`). GPU에서 fp16으로 돌려요.
- **왜:** 임베딩 검색은 질문과 문서를 따로 요약해 비교해서 세밀한 차이를 놓쳐요. 리랭커는 둘을 같이 읽어서 더 정확해요. VRAM도 여유가 있었어요 (10.4GB).
- **결과:**
  - 검색만: 1등 적중률 0.47→0.66.
  - 정답성 0.573→0.595, 검색 실패 29→18문항.
  - 비용: 응답 +0.04초, VRAM +1GB.

### 8번. RAG 문서 다시 변환 + 새 조각 v3: 보류

- **기술:**
  - **Docling** (`scripts/convert_docs.py`): PDF를 표 구조를 살린 마크다운으로 바꿔요. 별도 uv 환경에서 돌리고 OCR은 껐어요.
  - **조각 만들기** (`scripts/build_rag_chunks.py`): 문서마다 다르게 잘랐어요.

    | 문서 | 자르는 방식 |
    |---|---|
    | 고객 응대 가이드 | 머리말·쪽 번호를 빼고 "➃ 열차 오승 고객 응대" 같은 상황 항목마다 자름 |
    | 안내방송 매뉴얼 | 오타를 고친 최신 txt를 번호 붙은 방송 문안마다 자름 |
    | 서울역 혼잡도·보호기준 | Docling 마크다운을 제목 단위로 자르고 표는 통째로 둠 |
    | 열차사고 체크리스트 | 순서도 그림을 Gemma(비전)로 글로 옮기고 원문 글자와 대조, 갈래 2곳은 손으로 고침 |

- **왜:** 예전 조각은 OCR 글자를 500자씩 기계적으로 잘라서 표가 깨지고 여러 상황이 섞였어요. 열차사고 체크리스트는 그림이라 정답성이 0.21이었어요.
- **수정 과정:**
  - 800자로 잘랐더니 한 조각에 상황이 섞여 검색이 나빠져서("열차를 잘못 탄" 질문 0.79→0.38), 상황 항목 단위 + 500자로 바꿨어요.
  - 열기 암호가 있는 PDF 두 개(고객응대·안내방송)는 풀지 않고 기존 txt를 썼어요.
  - 배포용 암호화된 한글 파일 세 개는 사용자가 한글에서 PDF로 저장해 준 것을 썼어요.
- **결과:** 전체 0.596으로 7번과 같았어요. 열차사고 0.21→0.50, 안내방송 0.64→0.71로 올랐지만, 서울역은 0.63→0.29로 크게 떨어졌어요.

### 9번. 새 조각 v4 (서울역 표 정리): 보류

- **원인:**
  - Docling 표의 칸 맞춤 공백과 줄표 때문에 표 한 줄이 170자를 넘어, 조각마다 표가 한 줄씩만 들어갔어요 (서울역 조각만 114개).
  - "보 통", "심 각"처럼 글자가 띄어져 있어 "보통"으로 찾을 수 없었어요.
- **수정:** `tidy_markdown()`를 추가했어요. 표의 공백을 걷어내고, 칸·제목 맨 앞의 띄어진 글자만 붙여요. 처음에는 전부 붙였다가 "개표 및 홈"이 "개표 및홈"이 돼서 맨 앞만 붙이도록 좁혔어요. 조각은 322개가 됐어요 (서울역 114→67).
- **결과:** 정답성 0.613으로 가장 높지만, 충실도는 0.919로 7번(0.928)보다 조금 낮아요. 서울역·보호기준도 예전 조각보다 낮아요.
- **보류 이유:** 정해 둔 기준("충실도와 정답성 둘 다 7번보다 나을 것")에 미달이고, 열차사고 순서도 md는 아직 사람이 검토하지 않았어요.

## 3. 지금 서버 구성

### 3-1. 질문 하나가 처리되는 순서

```
질문(글 또는 음성)
 → ① 받아쓰기·분류 (Gemma 4 12B, llama.cpp)
 → ② 검색: 질문 다듬기 → 임베딩(A) + 글자 매칭 → 문턱 0.45 → 리랭커가 상위 20개 재정렬 → 상위 5개
 → ③ 답변 생성 (문서 5개 + 받아쓴 글, 음성은 다시 안 넣음)
 → ④ 문장 단위로 끊어 음성 합성 (Supertonic, GPU)
```

`.env`는 `sts_server/config.py`의 `_load_dotenv()`가 읽고, `from_env()`가 `STS_이름` 환경 변수를 `Settings`에 넣어요. 미리 지정한 환경 변수가 `.env`보다 우선이라, 평가할 때는 값 하나만 바꿔 시험할 수 있어요.

### 3-2. `.env` 주요 설정

```
STS_ENGINE=llamacpp
STS_MODEL=gemma4-12b / STS_QUANT=q4                       # Gemma 4 12B QAT 4비트
STS_RAG_BACKEND=hybrid                                    # 임베딩 + 글자 검색
STS_RAG_JSONL=…\train_data_standardized.jsonl;…\RAG_자료\rag_chunks.jsonl   # 예전 조각 유지
STS_RAG_EMBEDDING_MODEL=…\finetune\models\kr-sbert-ft     # A: 검색 미세조정
STS_RAG_MIN_SCORE=0.45
STS_RAG_TOP_K=5                                           # 문서 5개
STS_RAG_RERANKER=dragonkue/bge-reranker-v2-m3-ko          # 리랭커 (후보 기본 20개)
STS_QA_AUDIO=false                                        # 답변 단계 음성 빼기
STS_FALLBACK_TTS=supertonic
```

### 3-3. ① LLM: Gemma 4 12B QAT 4비트

- **기술:** Google 공식 QAT(양자화 인지 학습) 4비트 GGUF를 llama.cpp 서버(:8081)로 돌려요. QAT는 4비트로 압축될 걸 미리 알고 학습해서, 그냥 압축한 4비트보다 품질 손실이 적어요.
- **코드:**
  - `sts_server/models.py`: `gemma-4-12b-it-qat-q4_0.gguf`에 음성·이미지 인코더(`mmproj`)를 붙여요. `enable_thinking=False`로 생각 과정 출력을 꺼요.
  - `sts_server/engines/llamacpp.py`: `-ngl 999`(모든 층 GPU), `-fa on`(Flash Attention), `-c 8192`(문맥 길이).
- **왜 이 모델:** 같은 조건에서 가장 빠르고(1.27초) 가장 정확해요(0.595). q8+LoRA는 1.8배, Qwen 30B는 2.1배 느렸어요.
- **VRAM:** 서버 전체가 대기 10.4GB, 리랭커 포함 11.45GB예요. 16GB 안에서 여유가 있어요.

### 3-4. ③ 답변 단계 음성 빼기 (`STS_QA_AUDIO=false`)

- **코드:** `pipeline.py`의 `_qa_messages`에서 `audio = wav_path if self.s.qa_audio else None`. `prompts.py`의 `qa_user_text()`는 음성을 넣을 때만 "위 음성으로 한 질문 (받아쓰기: …)"으로 써요.
- **왜:** 받아쓰기·분류 단계에서 이미 음성을 한 번 들었어요. 답변 단계에서 다시 넣으면 음성 인코딩과 프리필이 두 번 일어나요.
- **실측:** 음성 응답 1.92→1.67초, 정확도 같음.

### 3-5. ④ 문장 단위 생성과 음성 합성

- **문장 단위 생성:** 답을 만드는 대로 문장 단위로 끊어요 (`SentenceSplitter`). 첫 문장이 16자를 넘으면 쉼표에서 먼저 끊어 합성을 일찍 시작해요 (`first_split_chars=16`). 최대 384토큰, temperature 0.7이에요.
- **겹쳐 처리:** 모델이 다음 문장을 만드는 동안 앞 문장을 합성해요.
- **Supertonic TTS GPU:** onnxruntime-gpu 1.26으로 바꿨어요. torch를 먼저 불러와야 torch의 cuDNN을 써요. pip cuDNN 9.27은 RTX 50 시리즈에서 오류가 나고 조용히 CPU로 돌아가요. `warm_tts()`로 서버 시작 때 한 번 합성해 둬요.
- **실측:** 답변 음성 준비 중앙값 3.73→2.48초, 최대 4.85→3.36초.

### 4-2. 문서 임베딩: KR-SBERT 미세조정본

**KR-SBERT란**
- 서울대 연구실(snunlp)이 공개한 **한국어 BERT를 문장 비교용(Sentence-BERT)으로 다시 학습한 모델**이에요.
- 그냥 BERT는 낱말을 이해하는 모델이라, 문장 벡터를 바로 코사인으로 비교하면 결과가 좋지 않아요. SBERT는 "뜻이 비슷한 문장은 벡터도 가깝게" 나오도록 추가 학습해서, 코사인 유사도가 곧 뜻이 비슷한 정도가 돼요.
- 이름의 `V40K`는 낱말 사전 약 4만 개, `klueNLI`는 KLUE 문장 추론 데이터, `augSTS`는 늘린 문장 유사도 데이터로 학습했다는 뜻이에요.

| 항목 | 값 |
|---|---|
| 모델 | `finetune/models/kr-sbert-ft` (원본 `snunlp/KR-SBERT-V40K-klueNLI-augSTS`) |
| 구조 | BERT-base: 12층, 768차원, 약 1.1억 개 파라미터, 파일 467MB |
| 입력 길이 | 256토큰 (`EMBED_MAX_TOKENS`). 원래 128이었는데 조각(약 450자)이 잘려서 늘림 |
| 문장 벡터 | 평균 풀링 + 정규화. 정규화하면 내적이 곧 코사인 유사도 |
| 캐시 | `data/rag_cache/<해시>.pt`. 모델·토큰 길이·문서 내용이 같으면 다시 계산하지 않음 |

```python
# sts_server/rag.py _embed()
hidden = self.model(**enc).last_hidden_state                  # 토큰마다 768차원
emb = (hidden * mask).sum(1) / mask.sum(1)                   # 실제 토큰만 평균 (평균 풀링)
out.append(torch.nn.functional.normalize(emb, dim=-1))       # 길이 1로 정규화 → 내적 = 코사인 유사도
```

**미세조정 내용 (A)**

| 항목 | 값 | 이유 |
|---|---|---|
| 학습 데이터 | 질문 2,661개 (학습 2,395 / 검증 266) | 글라스에 말하는 방식이 다양해서 문서마다 정식·반말·키워드·상황형 질문을 만듦 |
| 테스트 세트와 비슷한 질문 | 학습 데이터에서 뺌 | 점수 부풀림 방지 |
| 손실 함수 | MultipleNegativesRanking, scale 20 | 같은 묶음의 다른 문서와 헷갈리는 오답 문서를 오답으로 삼음 |
| 묶음 / 학습률 / 에폭 | 32 / 2e-5 / 3 (2에폭째 저장) | 검증 점수가 가장 좋은 에폭 |
| 검증 점수 (3위 안 적중) | 0.624 → 0.827 | `train_info.json` |

### 4-3. 검색 기준

```
① 질문 다듬기 → ② 하이브리드 점수 → ③ 문턱 0.45 → ④ 리랭커(상위 20개) → ⑤ 상위 5개 넘김
```

**① 질문 다듬기 (`normalize_query()`)**

| 바꾸기 전 | 바꾼 뒤 | 이유 |
|---|---|---|
| 스크린도어, 스크린 도어, 안전문 | PSD | 문서에는 "PSD"로 적혀 있음 |
| 엘베 | 엘리베이터 | 줄임말 |
| 오백일, 오백이십오 | 501, 525 | 음성 받아쓰기가 숫자를 한글로 쓰는 경우 |

**② 하이브리드 점수 (`scored()`)**

```
점수 = 코사인 유사도(임베딩) + 0.5 × 글자 점수(TF-IDF)
```

| 요소 | 방식 | 역할 |
|---|---|---|
| 코사인 유사도 | 질문 벡터와 문서 벡터의 내적 | 말을 바꿔 물어도 뜻이 같으면 찾음 |
| 글자 점수 | 글자 두 개씩 묶은 TF-IDF | 정확한 낱말과 숫자를 맞춤 |
| 숫자 가중치 | 두 자리 이상 숫자는 통째로 3배 더 (`NUMBER_WEIGHT=3`) | 505와 525를 구분 |
| 글자 점수 비중 | 0.5 (`LEXICAL_WEIGHT`) | 의미 검색 중심, 글자 검색은 보조 |

**③ 문턱 0.45:** 점수가 0.45보다 낮은 문서는 넘기지 않아요. 하나도 넘지 못하면 "참고자료 없음"으로 답해요. 관련 없는 문서를 넘기면 모델이 그걸 근거로 지어내기 때문이에요. 미세조정 후 점수 분포에 맞춰 0.5에서 다시 잡았어요.

**④ 리랭커**

리랭커는 코사인 유사도로 줄 세우는 것이 아니에요. 코사인으로 고른 후보를 **질문과 문서를 같이 읽는 별도의 모델**이 다시 채점해요.

| | 임베딩 (코사인) | 리랭커 (크로스 인코더) |
|---|---|---|
| 방식 | 질문과 문서를 따로 벡터로 바꿔 각도를 비교 | 질문과 문서를 한 입력으로 붙여 관련도를 직접 냄 |
| 속도 | 빠름. 문서 벡터를 미리 계산해 둠 | 느림. 질문마다 쌍을 새로 읽어야 함 |
| 정확도 | 비슷한 주제는 잘 찾지만 세밀한 차이에 약함 | 낱말 사이 관계까지 봐서 더 정확 |

| 항목 | 값 |
|---|---|
| 모델 | `dragonkue/bge-reranker-v2-m3-ko`: BAAI의 `bge-reranker-v2-m3`를 dragonkue가 한국어로 미세조정해 공개한 모델 (Apache-2.0). 우리가 직접 미세조정하지 않고 그대로 씀 |
| 구조 | XLM-RoBERTa large: 24층, 1024차원, 약 5.7억 개 파라미터 |
| 정밀도 | GPU fp16, VRAM 약 1GB |
| 입력 | [질문, 문서] 쌍, 최대 512토큰 |
| 점수 | 출력에 시그모이드를 씌운 0~1 |
| 후보 | 문턱을 넘은 상위 최대 20개 (`STS_RAG_RERANK_CANDIDATES`) |

규칙 (`ranked()`):
1. 하이브리드 점수 상위 20개 중 문턱을 넘은 것만 후보로 삼아요.
2. 후보가 2개 미만이면 건너뛰어요.
3. 리랭커 점수 순서로 다시 세워요.
4. 리랭커는 **순서만** 바꿔요. 넘길지 말지는 여전히 하이브리드 점수와 문턱이 정해요.

왜 이렇게 했나:
- 583건을 다 읽으면 느려서, 빠른 임베딩으로 20개까지 좁히고 정확한 리랭커로 순서만 다시 정해요. 계산은 약 33밀리초예요.
- 리랭커가 "문서 없음" 판정까지 바꾸면 모름 답이 흔들릴 수 있어서, 검증된 문턱을 그대로 뒀어요.

모델 카드의 비교표 (작성자가 직접 잰 수치라, 우리 문서에서도 같은 순서인지는 따로 재 봐야 함):

## 7. RAGAS 점수 읽는 법

- RAGAS 지표는 0~1 절대 점수로 정의돼 있지만, 실제 값은 **심판 모델, 테스트 세트, 정답 작성 방식**에 따라 크게 달라져요. 그래서 상대평가로 읽어야 해요.
- 같은 답을 다시 채점해도 ±0.01 정도 흔들려요. 그래서 버전끼리 ±0.01~0.02 차이는 "같다"고 봐요.
- 비교할 때는 심판과 문항을 고정해요. 이번 평가에서는 9개 버전 모두 같은 Gemma 심판, 같은 253문항을 썼어요.
- LLM 판단이 들어가지 않는 **검색 적중률**과 **응답 시간**은 절대 수치로 읽어도 돼요.

## 8. Opus 5.5 심판 비교 (2026-11-02~03)

### 8-1. 왜, 어떻게 했나

- **목적:** 심판을 Gemma(자기 답을 채점)에서 더 강한 다른 모델로 바꿔도 결론이 같은지 확인했어요. 문서 없는 대형 모델과 비교해 RAG가 얼마나 값어치가 있는지도 봤어요.
- **비교한 판:** Sonnet 5.5 (RAG 없음), 7번 (지금 `.env`), 9번 (새 조각 v4). 7·9번은 저장된 답을 다시 채점해서 서버는 켜지 않았어요.
- **방법:** API를 쓰지 않고, Claude Code 대화 안의 보조 에이전트로 처리했어요. 노력 수준은 둘 다 medium이에요.
  - **Sonnet 5.5 답변:** 253문항에 문서 없이 답했어요. 서버와 같은 말투 지침을 주되, "모르면 안내데스크" 규칙은 뺐어요.
  - **Opus 5.5 채점:** RAGAS와 같은 절차를 손으로 재현했어요.
    - **정답성:** 답과 정답을 주장 단위로 쪼개 서로 대조한 뒤 F1을 계산해요. 세 판의 답은 A·B·C로 이름을 가려서, 어느 모델 답인지 모르게 했어요.
    - **충실도:** 7·9번 답을 문장으로 쪼개고, 문장마다 검색된 참고자료로 뒷받침되는지 판정해요.
  - 판정은 파일로 남기고, 점수는 프로그램으로 계산했어요 (`tmp/claude_eval/score.py`).
- **참고:** 서버와 같은 엄격한 지침을 줬을 때 Sonnet은 253문항 중 193개(76%)를 "안내데스크에서 확인하실 수 있습니다"로 답했어요. 이 판은 기록만 남기고 채점하지 않았어요.

   - Sonnet은 정답에 없는 주장이 380개로 7번의 약 4배예요. 매뉴얼에 없는 내용을 그만큼 많이 덧붙였다는 뜻이에요.
2. **7번과 9번의 차이는 잡음 수준이에요.**
